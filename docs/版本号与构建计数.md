# 版本号与构建计数

本仓库的版本号有两层含义，**不要混用**：

- **营销版本**（`1.12.5`）：给人看的，功能层面变了才动。
- **构建号**（`122`）：机器用的，**等于累计编译次数**，每次编译必变。

构建号的口径是一句话：**只要发起过一次编译，就算一次构建，成功失败都算。**
本机编译和云编译各算各的 —— 同一天本机编 1 次、云端编 1 次，就是 +2。

---

## 1. 版本号是两个字段

| 字段 | 当前值 | 谁提供 | 语义 |
|---|---|---|---|
| `CFBundleShortVersionString` | `1.12.5` | `ios/VERSION` → 生成器写进 `MARKETING_VERSION` | 营销版本 |
| `CFBundleVersion` | `122` | `CURRENT_PROJECT_VERSION`，CI 每次编译注入 | 构建号 = 累计编译次数 |

营销版本号**只有一个来源**：仓库里的 `ios/VERSION` 文件（纯文本，一行）。
`scripts/gen-xcode-project.py` 读它，再写进 pbxproj 的 Release / Debug 两处。
改版本 = 改 `ios/VERSION` + 重跑生成器，别直接改 pbxproj。

两者都走**构建设置引用**，`Info.plist` 里写的是变量、不是字面量：

```
CFBundleShortVersionString = $(MARKETING_VERSION)
CFBundleVersion            = $(CURRENT_PROJECT_VERSION)
```

> ### 坑：营销版本号写在两个地方，漂了一次
>
> 这个值以前同时写在 pbxproj 和生成脚本里。有一次只改了 pbxproj（1.12.4 → 1.12.5），
> 脚本里还是 1.12.4。后面为了加源文件重跑生成器，pbxproj 被整份覆盖，
> 版本号悄悄退回 1.12.4 —— 直到校验 ipa 才发现，中间白编译了一次。
> 所以现在收成 `ios/VERSION` 一个文件，脚本读不到就直接报错退出，不猜。

> ### 坑：plist 写死字面量，xcodebuild 注入完全不生效
>
> `xcodebuild CURRENT_PROJECT_VERSION=101` 不会覆盖 plist 里写死的 `100`。
> 当时 tag 是 `build101`、包内 `CFBundleVersion` 还是 `100`，查了很久才发现
> 是 plist 没引用构建设置。这两行一旦写成数字，版本号就永远停在那个死数字上。

## 2. tag 命名

```
v<营销版本>.build<构建号>
```

例：`v1.12.5.build101`。

tag 构建的号**直接取 tag 名里的 `.buildN`**，不再累加。原因很实际：
tag 是快照，不能因为「重新跑一次 CI」就让号变掉 —— 同一个 tag 必须是同一个号。

tag 构建是 detached HEAD，只把号写进 run summary，不回写仓库。

---

## 3. 两个仓库共用一个号

Web 版（`deepseek-chatbox`）和本仓库共用同一套编译计数，不是各编各的：

- Web 版最后一个是 `v1.12.4.build87`
- 本仓库从 **88** 接着往下数

营销版本之所以从 `1.12.4` 跳到 `1.12.5`，是因为 iOS 是完全独立的实现
（C++ 核心 + UIKit），不是 Web 版的补丁，不该沿用同一个营销版本号。

---

## 4. 三者必须一致

包内 `CFBundleVersion`、`base + build-events.jsonl 的行数`、tag 里的 `.buildN`，
**永远是同一个数**。校验：

```bash
python scripts/bump-build.py --show
# build=122  base=110  events=12  since=2026-11-24 15:40 +0800

# 营销版本号：文件、工程、包内三处要一致
cat ios/VERSION                                  # 1.12.5
grep -m1 MARKETING_VERSION ios/ChatboxIOS.xcodeproj/project.pbxproj   # 1.12.5

# 包内版本号（不依赖 plutil / unzip，Windows 上也能跑）
python -c "import zipfile,plistlib;z=zipfile.ZipFile('dist/ChatboxIOS-adhoc.ipa');\
n=[x for x in z.namelist() if x.endswith('.app/Info.plist')][0];\
i=plistlib.loads(z.read(n));print(i['CFBundleShortVersionString'],i['CFBundleVersion'])"
# 1.12.5 122
```

对不上就是有一步没写回去：

- CI 的 `Record build count` 步骤没提交成功 → 远端行数偏少
- `Info.plist` 又写回字面量了 → 包内号不跟 CI 走
- 本地构建没记事件 → 本地算出来的号偏小

> **为什么不直接用 `unzip | plutil -p -`**：`plutil` 从 stdin 读不可靠，
> `unzip` 的路径通配也不稳（`Payload/*.app/Info.plist` 未必匹配得上）。
> 上面那段 Python 在 macOS 和 Windows 上行为一致。

## 5. 构建号怎么记

| 触发点 | 怎么记 |
|---|---|
| 本机 `cmake --build`（含增量、什么都没变也算） | CMake 的 `build_count` 目标自动追加一行 `local` |
| 本机 `ctest` | `build-local.sh` 追加一行 `test` |
| 云编译（Actions 每次 run） | workflow 追加一行 `ci`；分支构建号 = 追加后那行的号 |
| tag 构建 | 号直接取 tag 名里的 `.buildN`，只编译不回写 |

### 为什么本机「什么都没变」也要 +1

CMake 里用的是 `add_custom_target(build_count ALL ...)`，不是 `POST_BUILD`。

`POST_BUILD` 只在 target 真的重建时才触发 —— 改个测试文件就不记了，那就不叫
「编译了一次」。用 `ALL` 才能做到**每次 `cmake --build` 都记**，这才是要的口径。

### 为什么 `build-local.sh` 不再自己记编译

它只记 `ctest`。因为编译已经由 CMake 的 `build_count` 目标记了，
脚本再记一次的话，一次编译会被算成两次。

## 6. 为什么是「流水账」而不是一个数字

早先是 `build-count.json` 里一个 `build` 字段，本机和 CI 各自读出来 +1 再写回。
两边同时推进时 git 合并只能二选一，**两次编译只剩一次，号被吃掉**，
而且每次 push 都冲突。

现在拆成两个文件：

| 文件 | 作用 | 合并行为 |
|---|---|---|
| `build-count.json` | `base` + 口径说明 + 冻结的旧明细 | 不再被写，所以不冲突 |
| `build-events.jsonl` | 一次编译一行，只追加、不改写 | `.gitattributes` 里 `merge=union`，两边的行都保留 |

```
build = base + build-events.jsonl 的行数
```

本机 1 行 + 云端 1 行 = 号 +2，既不互相覆盖，也不再产生冲突块。

### `build-count.json` 字段

| 字段 | 含义 |
|---|---|
| `base` | 开始按事件留档之前的次数汇总（1~110 那段只有汇总，没有逐条明细），冻结不再变 |
| `since` | 开始按事件逐条留档的时间点 |
| `meaning` | 口径说明，随文件走，避免脱离文档就没人知道这数怎么来的 |
| `legacy_history` | 旧格式明细，冻结保留，不再追加 |

`legacy_history` 里有一条 `"n": "13~99"` 的**占位**条目：旧版本没有计数机制，
那 87 次编译没逐次留档，用占位文字补上，别让数字看起来断了一截。

### `build-events.jsonl` 一行长这样

```json
{"n":121,"at":"2026-11-24 20:43 +0800","source":"ci","result":"success","ref":"45395531079","note":"云编译 master"}
```

| 字段 | 含义 |
|---|---|
| `n` | 这次是第几次（= base + 本行之前行数 + 1） |
| `source` | `local`（cmake）/ `test`（ctest）/ `ci`（Actions） |
| `result` | `success` / `failed` —— **失败也算一次** |
| `ref` | CI run id 或 commit sha |
| `note` | 一句话说明这次编译在干什么 |

## 7. 工具与 CI

```bash
python scripts/bump-build.py --show          # 看当前号 + 最近几条
python scripts/bump-build.py --next          # 只算下一次的号（CI 取号用）
python scripts/bump-build.py --dry-run       # 只算不写
python scripts/bump-build.py --source local --note "..."   # 一般用不到，CMake 已自动记
```

CI 里的顺序（`.github/workflows/ios-build.yml`）：

1. `Allocate build number` —— 用 `--next` 只算不写，把号注入
   `xcodebuild CURRENT_PROJECT_VERSION=<N>`
2. `Build & Archive` —— 编译，号进包
3. `Record build count` —— **编译结束后**才追加事件行并回写 master

先算后写，是为了「编译失败也要记一行」—— 如果先写再编，编挂了就没有这次记录。

## 8. 踩坑合集

### `gh release upload` 报 `HTTP 403: Resource not accessible by integration`

workflow 缺 `permissions: contents: write`，`GITHUB_TOKEN` 默认只读。
补上之后还要注意：**对旧 tag 重跑没用** —— `gh workflow run --ref <tag>` 用的是
该 tag 当时那份 workflow，修好的 workflow 在更新的 commit 上。

正确补挂方式：`gh run download <run> -n ChatboxIOS-adhoc` 取产物，再手动 `gh release upload`。

### 提交信息里出现跳过标记，整次 push 的 workflow 被静默跳过

GitHub 对跳过标记是**全文匹配**，不只看标题行。在提交正文里写「带 xxx 防循环」
这种解释，也会让 workflow 被跳过，而且 `gh run list` 里**根本没有这条**，
只能靠「怎么没跑」才发现。

写提交信息时别在正文里提这个词。

### `$VAR` 后面紧跟中文标点会被 bash 吃进变量名

```bash
echo "build $BUILD_NUMBER，不推进"     # ✗ UTF-8 locale 下把全角逗号当成变量名的一部分
echo "build ${BUILD_NUMBER}，不推进"   # ✓ 一律写 ${VAR}
```

当时报 `BUILD_NUMBER?: unbound variable`，tag 构建在最后一步挂掉（ipa 已产出但没挂上 Release）。

### 本地和 CI 同时 +1 会撞号

改成流水账之前，本地 `bump-build.py` 和 CI 各自读+1写回，撞过号（本地 107 和 CI 107）。
现在本地只写 `local` / `test` 行、CI 只写 `ci` 行，`merge=union` 保证两边的行都在，
各管一段才不冲突。**教训：一个数只能有一个写入者。**
